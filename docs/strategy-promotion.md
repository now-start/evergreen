# 단일 전략 승격

결정일: 2026-09-10. 상태: **20% 기준 사용자 전환 승인 / 2.1.0 구현 / 운영 전환 미확인**.
전체 수익성 게이트 미통과·전진 페이퍼 미실행 사실을 설명한 뒤 사용자가
“20% 기준 실거래 전환 승인”으로 예외 전환을 승인했다. 이는 검증 통과나 수익 보장이 아니다.

## 1. 선택

준비 후보는 **`breakout-buffer-early3-v1` 한 개**다. 실험72 `early3`를 가리키는
동결 후보 식별자이며, 2.1.0 주문 실행기에서 선택할 수 있는 전략 ID다.
학습 모델이 아닌 규칙 전략으로, 재학습·모델 파일·시드 선택이 필요하지 않다.

실험71의57 완화형 `wide20`을 비교 기준으로 유지한다. 실험72에서 최근 네 조건 중
최저 합산 손익이 가장 높았고, 과거 최저 합산 손익도 소폭 늘었다. 그러나 이것은
두 구간·모든 조건에서 우월하거나 전체 실험 중 통계적으로 최적인 전략이라는 뜻이 아니다.
최근 1시간 지연은 악화됐고 과거 개선은 단일 계좌에 의존한다. 후보 선택은
다음 검증 대상을 좁히는 결정이지 미통과 게이트를 통과 처리하는 결정이 아니다.

## 2. 고정 계약

실행 근거: `research.experiments.buffer_improvement.POLICIES["early3"]`와
`research.experiments.relaxed_exits.simulate(..., "liquidation-buffer", ...)`.
동결 구현 기준 커밋은 `bd83796`이다. 후속 이식은 이 커밋과 실험72 소스 해시를
기준으로 회귀 비교하며, 후보 설정을 변경하면 같은 후보 버전을 재사용하지 않는다.
연구 결과의 `strategy=regime-mlp-v1` 표시는 재사용된 라우터 이름이다. 이 후보는
모든 진입 허용 점수를 상수로 넣으며 MLP 추론·장세 선택을 하지 않는다.

| 항목 | 고정 값·동작 |
|---|---|
| 시장·봉 | 업비트 KRW-BTC 현물, 확정1시간봉, UTC, 준비200봉 |
| 자금 | 계좌별 가상100만원, 원화/BTC 전액 전환, 레버리지·분할 없음 |
| 진입 | 현재 종가 > 이전168봉 고가 최대 ×1.001; 현재 봉은 채널에서 제외 |
| 초기 손절 | 실제 진입 시가 −6×원래 매수 신호 이전24봉 평균 TR |
| 수익 추적 시작 | 진입 후 확정 종가 고점 ≥ 진입 시가 +3×진입 TR |
| 추적 거리 | 6×max(진입 TR, 현재 봉 이전24봉 평균 TR); 청산선 하향 금지 |
| 추세 유예 | 이전24봉 평균 종가 > 그 전24봉 평균이면 수익 추적 청산 유예; 초기 손절은 유지 |
| 이탈 확인 | 손절/추적 조건의 연속2봉 이탈 확인 |
| 채널 청산 | 현재 종가 < 이전96봉 저가 최솟값 |
| 재진입 | 추가 청산 후 조건부48시간 저점 채널 리셋 대기;96시간 청산 채널과 별개 |
| 진입 예산 | 초기 손절가의 비용 차감 예상 자산이 계좌 고점80% 이상일 때만 진입 |
| 선제 청산 | 현재 종가−(1+추가 지연 봉 수)×이전24봉 TR의 비용 차감 자산이 고점80% 이하이면 예약 유지 |
| 계좌 중단 | 평가 자산이 보존된 고점 대비20% 이상 하락하면 영구 중단; 체결 갭으로 초과 손실 가능 |
| 모의 체결 | 신호 다음 시가; 지연 조건은 추가1시간. 같은 신호 종가 체결 금지 |
| 기본 비용 | 매수·매도 각각 수수료0.05%, 슬리피지0.1%; 최소5000원·수량1e-8 |
| 대조 조건 | 기본 / 슬리피지2배 / 수수료·슬리피지2배 / 추가1시간 지연 |

20%는 **관측 중단 기준**이며 최대 손실 보장치가 아니다. 사용자 승인에 따라
새 전략은 정확히20%, 기존 전략은 최대10% 설정을 허용한다. 수수료·최소 주문 등은
실거래 시 실제 거래소 응답으로 다시 확인해야 하며 연구 값을 그대로 사용하지 않는다.

## 4. 2.1.0 실행 구조와 차이

- `strategies/buffer.py`: 순수 전략 상태. 진입 TR·체결 기준가·고점·청산선·이탈 횟수·리셋·청산 예약·봉 커서.
- `research/buffer_replay.py`: 같은 상태를 모의 체결 이벤트로 구동.35계좌×4조건의
  전체 JSON(체결·거절·자산 곡선 포함)140건이 동결 실험72와 일치했다.
- `trading/buffer_execution.py`: 확정봉 순차 복구와 실제 체결 대사. 실제 매수는
  신호 다음 시가를 얻을 수 없으므로 **확인된 체결 VWAP**을 진입 기준으로 쓴다.
  진입 TR은 주문 의도에 저장한 원래 신호 값이다. 모의 체결과 실거래 수익의 동일성을 보장하지 않는다.
  실제 최종 매수 체결 시각도 저장해 체결 전 시가를 보유 자산 고점으로 계산하지 않는다.
- `trading/state.py`: 기존 JSON payload에 전략·보호 상태·주문 문맥을 저장한다.
  테이블 DDL은 변경하지 않아 Alembic revision 추가가 필요 없다. 기존 payload는 기본 전략으로 읽는다.
- 미확정 주문은 기존 identifier 조회·잔고 대사부터 처리한다. 재POST하지 않는다.
  부분 매수는 확인된 실제 수량에 보호 상태를 만들고, 부분 매도는 남은 수량의 청산 예약을 보존한다.
  체결 시각 누락·미래 시각·여러 시간봉에 걸친 체결은 중단하고 pending을 보존한다.
  위험 청산의 시각 하한은 평가한 UTC 시간봉으로 두어 초 단위 체결을 로컬 마이크로초와 혼동하지 않는다.
-200개 확정봉 범위 안에서 필요한169봉 이력이 있는 누락 구간만 순차 복구한다.
  더 긴 공백·보호 상태 누락은 초기화하지 않고 중단한다. 관측된 과거 낙폭 중단도 보존한다.
- 진입은 신호 유효 시간 안에서만, 이미 예약한 청산은 다음 사이클에서도 유효하다.
  청산도 최신 호가·잔량·슬리피지·DB 소유권 검사를 통과해야 하며 실패 시 워커가 중단될 수 있다.

## 5. 검증 조건과 사용자 예외 승인

1. **공통 상태 전이 이식 및 재현**: 확정봉·실제 모의 체결 이벤트를 입력으로 하는
   후보 상태를 분리한다.35계좌×4조건의 신호·체결·거절·자산 결과가 기존72와
   일치해야 한다. 기존 `breakout-v1`도 회귀 통과해야 한다.
2. **복구·멱등성 검증**: 봉 중복/누락, 재시작, 청산 예약 중 장애, 부분 체결,
   주문 응답 유실, 외부 잔고 변경, 다중 워커에서 중복 주문0·대사 불일치0을 요구한다.
   상태를 잃으면 현금 계좌로 간주하지 않고 중단한다.
3. **전진 페이퍼**: 실제 주문 권한 없이 별도 가상 원장으로 실행한다. 실행 시작
   다음 완성 봉부터를 검증 구간으로 고정하며 이미 관찰한 데이터로 소급 시작하지 않는다.
   후보·wide20·원래 운영 돌파를 동시에 비교하고 같은 실제 도착 데이터/지연을 기록한다.
   최소90일과 후보 자연 청산10회 모두 충족 전 성과 판정하지 않는다. 기간 중
   임계값 변경 시 새 후보 버전과 새 검증 구간으로 다시 시작한다.
4. **수익·위험 승인**: 기존72의 최근/과거·네 조건 전체 개선 게이트 실패를
   그대로 기록한다. 전진 페이퍼 통과만으로 이 실패를 지우지 않는다. 유지할 기준은
   기존 문서대로 대응 중앙값·양수 계좌 과반·낙폭·중단·거래 수를 함께 본다.
   페이퍼 단일 계좌는 기존35계좌 게이트를 대체하지 않는다. 후보 변경이나 기준
   변경이 필요하면 사전 재설계·새 미관측 평가와 사용자 승인 없이 승격하지 않는다.
5. **예외 전환 승인**: 사용자는 전체 게이트 미통과·전진 페이퍼 미검증을 인지하고
   20% 기준 실거래 전환을 승인했다.1–2의 구현 검증을 수행하되3–4가 통과했다고 기록하지 않는다.
   별도 투자금 증액·DB 자산 고점 초기화·중단 해제는 승인 범위에 포함하지 않는다.

페이퍼 관찰 항목은 후보 버전, 마지막 확정봉, 데이터 신선도, 신호 원인, 모의 체결
지연/비용, 보유 상태, 청산 예약, 자산/낙폭 및 중단 이유다. 아직 대시보드·상시
페이퍼 프로세스를 구축하거나 이90일 검증을 시작하지 않았다.

## 6. 배포 순서·중단·복귀

Config Server의 `evergreen.execution`에 필요한 변경은 다음 두 값이다.
키·DB·live-enabled·기타 제한은 변경하지 않는다.

```yaml
strategy: breakout-buffer-early3-v1
max-drawdown: 0.20
```

**먼저2.1.0 이미지 배포를 확인한 후 설정을 반영한다.**2.0.2는20% 설정을 거부한다.
CI·이미지 발행·GitOps 반영·실제 서비스 태스크 전환은 각각 확인 대상이다.
이 문서의 구현·오프라인 검증만으로 이 단계들이 완료됐다고 간주하지 않는다.

운영자가 설정 반영 후 앱을 재시작하면 미확정 주문 대사 후 기존 상태를 유지한다.
기존 BTC는 기존 전략(최대10% 중단)으로 계속 관리하며 새로 인수하지 않는다.
현금 상태(BTC≤1e-8)·중단 아님·미확정 주문 없음이 확인된 사이클에만
`event=strategy_transition from=breakout-v1 to=breakout-buffer-early3-v1`을 기록한다.
전환 사이클은 주문하지 않고 다음 시간봉부터 새 전략을 평가한다.
최소 주문액 미만이지만1e-8 초과인 기존 잔량은 자동 처리하지 않으므로 별도 대사가 필요하다.

장애 시 워커를 중지하고 미확정 주문·잔고·DB 상태를 대사한다.
**새 JSON 필드는2.0.2의 extra-forbid와 호환되지 않으므로 이전 이미지 자동 롤백은 금지한다.**
기본 전략 복귀도2.1.0 코드에서 현금·미확정 주문 없음 확인 후
`strategy: breakout-v1`, `max-drawdown: 0.10`으로 수행한다.
보유 중 설정만 바꾸어 기존 전략으로 강제 인수하지 않는다. 보유 중10%로 낮추면
더 엄격한 중단이 즉시 적용될 수 있다. `halted`, 자산 고점, pending 삭제·재초기화는 하지 않는다.
