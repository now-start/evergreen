# 거래 워커 재시도·복구 정책

API 내장 워커와 CLI `--execute`는 동일한 `trading.runtime.run` 감독 루프를 사용한다.
SDK·SQL 호출 각각에 재시도 데코레이터를 붙이지 않는다. Upbit SDK의 `max_retries=0`과
주문 의도 선저장 원칙을 유지하며, **POST를 다시 보내는 재시도는 없다.**

## 공통 흐름

주문 보류·기존 API/DB 자원 정리 → 원인·대기 시간 보고 → 대기 →
새 DB 세션에서 실행 잠금 획득 → 저장 상태 읽기 → 미완료 주문 우선 대사 →
정상 평가 사이클에서 잔고·최신 호가 검증 → 현재 시점 판단.

- 모든 거래 루프 오류는 같은 경로로 재검증한다. 영구 차단·보고 전용 루프는 없다.
- 기본 대기는 5 → 10 → 20 → 40 → 60초, 이후 최대 60초 간격이다.
  성공한 평가 사이클만 연속 실패 횟수를 초기화한다. 연결 성공만으로 초기화하지 않는다.
- 인증/권한·기타 요청 거절, 주문 조회 404, 418/429, DB 상태 검증·알 수 없는 오류는 최소 60초 대기한다.
  408·418·429·5xx의 `Retry-After`가 더 길면 해당 대기 시간을 지킨다.
- 취소/서버 종료는 백오프 중에도 즉시 전달하고, 기존 자원 정리가 끝나기 전에 새 세션을 열지 않는다.
- 정리 중 2차 오류가 발생하더라도 원래 오류의 원인 코드와 대기 기준을 보존한다.
- 한번만 실행하는 `--once`와 최초 설치 승인 명령은 실패를 즉시 반환한다. 자동 반복 실행하지 않는다.

## 동일한 복구 경로에서 지키는 검증 조건

| 종류 | 정책 |
| --- | --- |
| 거래소 연결/타임아웃, 408/418/429/5xx | 백오프 후 전체 복구 경로 재진입 |
| DB 연결 단절·잠금 미확보/상실·교착/잠금 시간 초과 | 연결을 새로 열고 잠금부터 재확보 |
| 인증·권한 오류 | 최소 60초마다 재확인. 키 자체를 교체했다면 Config Server를 다시 읽도록 재시작 필요 |
| 미완료 주문 조회 404 | 기존 주문 의도를 유지하고 최소 60초마다 조회. 404만으로 의도를 지우거나 새 주문을 보내지 않음 |
| 오래된 호가·신호, 호가 정렬/잔량 부족, 슬리피지·주문 금액 범위 초과 | 주문을 보류하고 공통 백오프 후 상태부터 다시 확인 |
| 체결 후 잠금 잔고 해제 대기, 엔진 확정 봉 품질 검증 실패 | 백오프 후 재확인 |
| 잔고·계정·주문 식별자 불일치, DB 상태 누락/손상, 알 수 없는 오류 | 같은 검증을 반복하고 실패하면 계속 주문 보류. 원인이 해소되어 검증을 통과하면 자동 재개 |
| 손실 한도 도달 | 기존 `halted` 상태·위험 청산 정책을 유지. 자동 초기화/해제하지 않음 |

오류 종류는 원인 코드와 대기 시간에만 영향을 주며, 자동 재검증 여부를 바꾸지 않는다.
알 수 없는 오류는 메시지 문자열로 추측하지 않고 `revalidation_required`로 보고한다.
예를 들어 주문 의도 저장 이후 전송 전에 호가가 만료된 경우도 기존 의도를 자동 삭제하지 않는다.
잔고 불일치는 기존 잔고·원금·고점을 보존하고 매번 대조한다. 일치하지 않는 동안 주문하지 않는다.
새 잔고 불일치만으로 영구 `halted`를 저장하지 않는다. 기존에 저장된 `halted`나 손실 한도에
의한 `halted`는 자동 해제하지 않는다. 따라서 과거 버전에서 이미 중단된 계좌를 임의로 재개하지 않는다.
자동 재검증은 원인을 자동 수정한다는 뜻이 아니다. 손상된 DB·누락된 승인·잘못된 키는
운영자가 바로잡아야 하며, 그 전까지 검증이 계속 실패하므로 주문은 보류된다.
상태를 지우거나 손실 한도를 초기화하는 복구 명령은 추가하지 않는다.

복구 중에도 지나간 매수 신호를 몰아서 실행하지 않는다. 기존 확정 봉 복구·신호 유효 시간·
청산 예약·주문 전 잠금 확인이 그대로 적용된다. 대기 주문의 정상 조회는 `pending`이며
새 주문을 허용하지 않는다. `worker_recovered result=pending`도 체결 완료를 뜻하지 않는다.

## 관측

- `worker_recovering`: 이유, 예외 타입, 연속 실패 횟수, 다음 시도까지 초.
- `worker_recovered`: 복구 후 처음 완료한 사이클 결과.
- `/actuator/info.trading`: `status=running/recovering/halted`, `reason`,
  `error_type`, `attempt`, `retry_seconds`, 마지막 정상 `last_cycle_at`.
- 기동 설정 검증 실패 등 감독 루프 밖의 오류는 기존 `failed` 상태로 구분한다.
- `/actuator/health`는 프로세스 생존 확인이다. 워커 장애만으로 컨테이너를 무한 재시작시키지 않는다.
- 인증 값·주문 원문·예외 메시지는 로그에 넣지 않는다. 복구 중에는 새 손익 평가가 없을 수 있으므로
  대시보드의 마지막 관측 시각과 워커 상태를 함께 확인한다.

Grafana 템플릿의 마지막 워커 카드와 운영 로그 조회도 위 두 복구 이벤트를 포함한다.
실서비스 대시보드 적용과 애플리케이션 배포는 별도 배포 단계에서 수행한다.

## 2.2.3 배포 순서

1. 검증·리뷰한 변경을 Evergreen `main`에 커밋·푸시한다.
2. 해당 커밋의 App CI 성공, 정식 릴리스 `2.2.3`, 이미지의 `linux/amd64`·`linux/arm64` 발행을 확인한다.
3. 그 후 GitOps `evergreen/docker-compose.yml`의 coin 이미지만 `ghcr.io/now-start/evergreen:2.2.3`으로 올린다.
   `NOW_START` 고정, 1 replica, `stop-first`, 3분 롤백 감시는 유지한다.
4. Portainer 동기화와 실제 서비스 이미지·태스크 업데이트 완료를 별도로 확인한다.
   순단 뒤 기존 DB 상태와 미완료 주문을 대사하므로 실행 상태를 초기화하지 않는다.
5. `/actuator/info`의 버전과 `trading.status`, `last_cycle_at`, 워커 heartbeat를 확인한다.
   최소 3분간 워커를 관찰한다. `recovering`이 지속되면 이유·대기 시간·상태 검증 결과를 확인한다.
   health 200이나 Swarm 업데이트 완료만으로 거래 루프가 정상이라고 판단하지 않는다.
6. 기존 Grafana 대시보드에 템플릿의 복구 이벤트 조회·표시를 적용한다. DB 연결은 추가하지 않는다.

이번 버전에는 Config Server 값·DB 스키마·전략·손실 한도 변경이 없다.
롤백이 필요하면 발행된 이전 이미지 `2.2.2`로 GitOps를 되돌리고 같은 배포 검증을 수행한다.
DB나 주문 이력을 되돌리지 않는다. 이전 버전에서는 오류 후 워커가 다시 멈출 수 있다.
위 단계는 배포 절차이며 실행 완료를 의미하지 않는다.
