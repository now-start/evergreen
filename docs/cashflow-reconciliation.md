# 원화 입출금 자동 대사 (2.2.4)

완료된 원화 출금 이후 `unexpected_balance`가 반복되는 문제를 해결한다.
주문이 미확정 상태가 아니며 BTC 수량이 동일할 때, 마지막 검증된 장부 잔고부터
완료된 KRW 입출금을 조회한다. 입금액 − 출금액 − 수수료가 실제 잔고 차이와
0.01원 이내로 일치하고, 다시 조회한 잔고·잠금·미체결 주문 검증도 통과해야 반영한다.
대사 사이클에서는 주문하지 않고 다음 사이클에서 새로 검증·판단한다.
검증된 기존 잔고가 있으면 정상 사이클에서도 이력을 조회하므로, 입출금이 상쇄되어
잔고가 같아진 경우에도 자금 이동과 수수료를 기록한다.

## 조회 및 감사

- 공식 [입금 목록](https://docs.upbit.com/kr/reference/list-deposits)의 `ACCEPTED`,
  [출금 목록](https://docs.upbit.com/kr/reference/list-withdrawals)의 `DONE`만 사용한다.
- 기존 API 키에 **입금조회·출금조회** 권한이 필요하다. 출금 실행 권한은 필요하지 않다.
- UUID 커서로 양쪽 이력의 끝까지 조회한다. 중복 페이지, 잘못된 상태/통화/시각,
  이력 한도 초과 또는 조회 오류는 추측해서 보정하지 않고 기존 재시도 정책을 따른다.
- 조회 한도는 종류별 10,000건, 한 번에 반영할 내역은 100건이다.
- 마지막 `initialized`, `order-terminal`, `cashflow-reconciled` 이벤트의 시간과
  잔고/계정/주문 순번을 기준으로 한다. 반복 거절·평가 기록은 이 기준을 이동시키지 않는다.
- 기준 시간 이전에 요청해 이후 완료된 이체는 잔고 반영 시점이 모호하므로 자동 반영하지 않는다.
- 실행 상태와 `cashflow-reconciled` 감사 이벤트를 기존 DB 잠금·트랜잭션으로 함께 저장한다.
  재시작은 새 기준에서 이어가므로 같은 이체를 중복 반영하지 않는다.
  일반 로그에는 건수만 기록하고 상세 금액·UUID는 DB 감사 이력에 저장한다.

## 위험 및 손익

입출금은 외부 자금 이동이다. 최초 원금은 보존하고 순입출금액을 별도로 누적한다.
총손익은 `현재 순자산 − 최초 원금 − 순입출금액`, 총수익률은
`총손익 / 최초 원금 × 100`이다. 이는 최초 원금 대비 누적 손익률이며 시간가중수익률은 아니다.
입출금 수수료는 실현 비용이고, 주문 수수료와 별도 `transfer_fees_krw`로 노출한다.

입출금에 맞춰 자산 고점을 비례 보정해 출금 원금 자체가 낙폭으로 계산되지 않도록 한다.
출금 수수료는 자금 회수 전 비용으로 반영한다. 입금 전 이미 손실 한도를 넘었거나
기존 `halted`가 참이면 중단을 유지한다. 전액 출금은 잔고와 고점이 0이 되며,
`empty_peak_ratio`에 기존 낙폭 비율을 보존해 재입금으로 손실 이력을 지우지 않는다.
전략 상태, 주문 순번, 예약 신호를 초기화하지 않는다.

손익 장부는 실제 자금 변동 이벤트만 재생한다. 과거의 반복된 거절 로그는 자금 이동이
아니므로 합산에서 제외한다. 주문/입출금 이력과 실제 잔고가 불일치하면 여전히
`unavailable`이며 임의의 수익을 표시하지 않는다.

## 범위와 배포 확인

이번 자동 대사는 KRW 입출금에 적용한다. BTC 입출금·수동 거래, 미확정 주문 정산 중
불일치, API 이력에 나타나지 않는 원화 이용료 입금은 자동 인수하지 않는다.
원화 이용료를 입금으로 간주할 근거가 없으면 설명되지 않는 잔고 차이로 남긴다.

2.2.4 이미지 배포 후 `cashflow_reconciled`와 다음 정상 `trading_cycle_result`,
`/actuator/info.trading`을 확인한다. 운영 DB 초기화나 수동 잔고 덮어쓰기는 필요하지 않다.
테이블 변경은 없지만 JSON State에 `empty_peak_ratio`가 추가되어 이전 버전은
`extra=forbid` 검증으로 읽지 못한다. 상태를 삭제하여 롤백하지 말고 호환 코드로 배포한다.
